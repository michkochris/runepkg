Your gut instinct is spot-on. A low-level tool shouldn't be making smart, state-mutating assumptions or dumping raw unpacked contents into a shared system state directory like /srv/lib/runepkg_dir unless you explicitly ask it to or it's part of a distinct high-level install/inspect workflow.

In package managers (like dpkg-deb --raw-extract / --extract or ar + tar), unpacking and installing/registering are two different layers of abstraction. In a minimal C89 CLI, -u / --unpack should be predictable, explicit, and side-effect-light.

Why /srv/lib/runepkg_dir Feels Off Here
Directories like runepkg_db, control_dir, build_dir, and download_dir belong to managed state and lifecycle orchestration—tracking installed packages, resolving dependencies, or caching artifacts.

If -u foo.deb silently drops files into /srv/lib/runepkg_dir/...:

Hidden side effects: Running a low-level unpack shouldn't pollute system state or look half-registered in a database/control directory.

Collision & cleanup headaches: Without an explicit target (or a clear convention), multiple unpackages or test runs step on each other or leave orphaned directories in /srv/lib.

Mismatch with -b: Since -b expects you to manually stage a .drb directory rather than relying on magical state, -u being "smart" or state-coupled breaks the symmetry of the low-level design.

How Low-Level -u / --unpack Should Behave
Think of -u as the read/extract primitive—taking a .deb archive (which under the hood is an ar archive containing debian-binary, control.tar.*, and data.tar.*) and materializing its contents cleanly without touching runepkg_db.

1. Explicit Destination (with a Safe Default)
Best low-level behavior: Accept an optional target directory argument (e.g., runepkg -u pkg.deb ./out_dir or -o <dir> depending on your flag grammar).

If no destination is given: Unpack into a current-directory-relative target derived from the package name/filename (e.g., ./<pkg>_unpacked or ./<basename>), not /srv/lib/....

Never overwrite silently: Fail cleanly (non-zero exit code + clear message to stderr) if the target directory already exists and is non-empty, unless a force flag is passed.

2. Clear Layout of Unpacked Contents
A .deb has two distinct halves—package metadata (control) and payload filesystem (data). Keeping them separate inside the unpacked target makes inspection and re-staging straightforward:

<dest>/data/ (or rootfs files) — extracted contents of data.tar.*

<dest>/control/ (or DEBIAN/) — extracted contents of control.tar.* (control, postinst, md5sums, etc.)

3. No Database or Lifecycle Hooks
Do not update runepkg_db.

Do not run maintainer scripts (preinst, postinst, etc.)—that's execution/installation, not unpacking.

Keep file permissions and symlinks intact where possible (with sensible safety checks against path traversal like ../ in tar entries, which is especially worth getting right in C89).

4. Symmetry with -b and .drb Staging
Since -b requires you to manually stage a .drb directory to build a .deb, -u becomes a natural companion if it produces a clean, inspectable directory tree that you can inspect, tweak, or feed into your staging/build pipeline—rather than burying it inside /srv/lib/runepkg_dir. (Even better: if you ever want a "smart" unpack into a managed workspace or cache, make that a separate flag or a high-level C++ FFI helper built on top of the low-level unpack primitive.)

A Quick Sanity Checklist for Your C89 Implementation
When you revisit -u in C89:

Archive parsing: Verify debian-binary and locate control.tar.* and data.tar.* cleanly, returning explicit error codes on malformed archives.

Path safety: Reject or sanitize .. path components and unexpected absolute paths during extraction.

Exit codes & stderr: Print diagnostics to stderr and return distinct non-zero exit codes on I/O, format, or destination errors so scripts and tests can rely on them.
