Portable Static musl Rescue Runner & Safe Matryoshka Deployment Engine
Deployment strategy and architectural plan for dropping a static musl runepkg & runas binary suite onto any unknown Linux environment (Debian, Kali, Ubuntu, etc.) to safely extract and configure a working core libc6 alongside target packages (such as file), maintaining full operational survival and bidirectional harmony with host dpkg/apt.
User Review Required & Critical Guardrails
Important
Static musl Rescue Binary Suite (make musl-all) The runepkg and runas binaries MUST both be compiled as zero-glibc static binaries via make musl-all (using x86_64-linux-musl-gcc and x86_64-linux-musl-g++ with static zlib and libcurl). Updated forge-musl-all.sh targets build (both runepkg and runas) to guarantee zero dynamic linkage to /lib64/ld-linux-x86-64.so.2 or libc.so.6.
Warning
Live Root (/) Mutation Gatekeeping & Container Isolation By default, runepkg -i <pkg> on live / activates the runepkg_antimatter_shield_check() safety lock on core packages (libc6, libgcc-s1, ld-linux*). Deploying a new libc6 directly onto live host / requires passing the explicit CLI flag --allow-core-runtime-on-root (or targeting an isolated --sysroot=/srv/lib/runepkg_dir/target_sysroot). Crucial Precaution: Live-root libc.so.6 swaps are delicate. Always test full libc6 + file deployments inside a sysroot or throwaway container first, keeping a rescue snapshot ready before running --allow-core-runtime-on-root on a live root.
Caution
Atomic In-Flight Swap & Usr-Merge Symlink Invariants Replacing live shared objects (e.g., libc.so.6) MUST NOT truncate existing files in-place or unlink structural directory symlinks (/lib64 -> usr/lib64). Extractions MUST write to same-directory temporary files (.runepkg_tmp_PID) and execute an atomic rename(2) swap to preserve active host processes.
Important
Host dpkg/apt Lock Checking & State Harmony When dpkg_host=auto writes stanzas to /var/lib/dpkg/status and file lists to /var/lib/dpkg/info/<pkg>.list:
1.
Lock Verification: runepkg MUST verify that host /var/lib/dpkg/lock-frontend and /var/lib/dpkg/lock are unlocked (no concurrent apt or dpkg process running).
2.
State Exactness: Package version, architecture, status (install ok installed), and dependencies MUST be exact.
3.
Validation: Always run apt-get check immediately after syncing to verify complete state agreement before running apt upgrade.

Deployment & Execution Workflow (Matryoshka Sequence)
 Step 1: Drop static musl `runepkg` & `runas` rescue binaries onto target Linux system.
                             |
 Step 2: Invoke `runepkg -i file.deb --allow-core-runtime-on-root` (or via --sysroot).
                             |
 Step 3: Resolution Engine builds 3-Stage Dependency Graph:
         - Stage 0: libc6, ld-linux-x86-64.so.2, libgcc-s1
         - Stage 1: libc-gconv-modules-extra, libmagic1t64
         - Stage 2: file
                             |
 Step 4: Pass 1 (Atomic Extraction Bottom-Up):
         - Unpack Stage 0 (.runepkg_tmp_PID + rename(2) atomic swap over libc.so.6)
         - Unpack Stage 1 (modules & libmagic)
         - Unpack Stage 2 (file executable)
                             |
 Step 5: Pass 2 (Configuration & Triggers Bottom-Up):
         - Run ldconfig & Stage 0 postinst
         - Run Stage 1 postinst
         - Run Stage 2 postinst
                             |
 Step 6: Host Entanglement Sync & Validation:
         - Verify /var/lib/dpkg/lock-frontend is free
         - Write status stanzas to /var/lib/dpkg/status
         - Write file lists to /var/lib/dpkg/info/*.list
         - Immediately run `apt-get check` to verify zero broken package warnings
                             |
 Step 7: System Equilibrium Verification:
         - Verify `file /bin/bash` runs cleanly.
         - Verify `apt upgrade` reports 0 broken packages and operates harmoniously.
