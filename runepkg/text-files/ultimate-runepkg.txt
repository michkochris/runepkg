The core breakdown of why runepkg build-toolchain is bleeding time on every package boils down to a fundamental mismatch between how Debian source packages expect to build and how a raw scratch toolchain presents itself.

When you inject a pristine, freshly bootstrapped GCC/musl toolchain and start pushing raw Debian source packages through it, you hit three massive architectural walls:

The Build System Assumption Wall: Debian source packages (.dsc) are deeply intertwined with the Debian build ecosystem (debhelper, dpkg-buildpackage, dh_auto_configure, etc.). They expect a glibc host environment, specific multi-arch paths, and standard GNU build system helper scripts. When stripped of those or forced into a bare musl sysroot without a full Debian chroot/dpkg environment, Autotools, CMake, and Meson scripts fail on obscure macro checks, missing header paths, or hardcoded assumptions about /lib/ld-linux*.so.*.

The Dependency Staging Fallacy: Staging build-dependencies by just throwing headers and libraries into a flat sysroot (/mnt/runepkg/.../sysroot) breaks packages that rely on pkg-config, .pc files with absolute host paths, or libtool .la files that point back to /usr/lib. When a Makefile invokes pkg-config --cflags foo, it either looks at the host or fails because the cross-sysroot's PKG_CONFIG_LIBDIR isn't strictly enforced with the correct cross-search paths.

Implicit Host Pollution & Missing Stubs: Even with environment sanitization, many upstream source packages have non-portable Makefiles that hardcode /usr/include, run host-side binaries during the build (which immediately segfaults when cross-compiling), or lack stubs for musl-specific missing functions (like musl lacking certain glibc-specific extensions like strndupa, backtrace, or specific shadow password structs).

The Pivot: Aligning with Debian's Native Cross-Building Model
To stop wasting 20–30 minutes per package debugging compile errors, build-toolchain needs to shift from a naive "scratch-build everything from source against a bare sysroot" approach to a Debian-native cross-compilation pipeline leveraging Debian's own multi-arch and cross-building flags (dpkg-architecture).

Instead of reinventing the wheel inside a custom scratch toolchain for every package, structure the build phase around how Debian officially handles cross-compilation:

Embrace Multi-Arch Tuples & dpkg-cross Logic: Debian packages natively support cross-compilation via DEB_HOST_GNU_TYPE and DEB_BUILD_GNU_TYPE. Instead of forcing raw CC/CXX overrides that break complex upstream Makefiles, pass standard Debian cross-wrapper variables (DEB_HOST_GNU_TYPE=x86_64-linux-musl or similar) so build systems invoke x86_64-linux-musl-gcc automatically through standard Debian helper abstractions.

Isolate via Light Chroots or Rootfs Overlays (Not Raw Sysroot Splice): Rather than bleeding files directly into a shared sysroot where pkg-config gets confused, treat each target profile as a mini-Debian rootfs (debootstrapped with musl/target compatibility) where apt or runepkg installs pre-compiled target dependencies as actual .deb packages (-dev fragments), rather than manual header/library staging. If a dependency isn't cross-compiled yet, runepkg should pull the binary .deb for the target architecture from the repository (or cross-build it once, package it as a .deb, and install it into the target rootfs).

The JIT matrix.bin Override Layer: Since you already have a working JIT engine and matrix.bin driven by build.txt, use it to specify per-package patch/override flags rather than generic compilation.
