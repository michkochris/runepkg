The short version: the files don’t show that all three installs should produce identical filesystem changes. They show that they should follow the same ELF and symlink rules, while operating on different roots and package states. The discussion file makes that distinction; the terminal log is an example of it.

What the discussion is saying
A dynamic linker symlink must resolve correctly inside the filesystem root being used. A staged install, a cross-architecture target, and the live host each have their own root and package state. So the principle is shared—provide a valid linker for that root—but the paths and whether runepkg should modify them need not be identical. In particular, treating the live host like an empty staging directory could disturb packages managed by the host’s existing package manager. (discussion, lines 7–22)

What the log demonstrates
The native install checks the linker under its staging directory: /srv/lib/runepkg_dir/install_dir/... (log, lines 154–155).
The ARM64 run uses a separate target tree and checks its linker there: /mnt/runepkg/aarch64-linux-gnu/.... That’s the same kind of check in a different root. (log, lines 184–187 and 222–223)
The later host run is different: runepkg reports shielding libc6 and plans eight packages instead of the earlier nine. That is consistent with the host already having different package state and with a deliberate safety policy—not evidence that the staging and target runs must match byte-for-byte. (log, lines 277–283)
One thing worth investigating
During the ARM64 run, the graph is written beneath /mnt/runepkg/aarch64-linux-gnu/..., but the log says the packages were downloaded to /srv/lib/runepkg_dir/download_dir. (log, lines 184–203) That may be an intentional shared download cache. If it isn’t, it’s a path-isolation issue to check. The printed configuration also changes between runs, so compare the effective config and database paths for each invocation before treating their results as a controlled comparison.

Useful comparison criterion: for each root, verify that the intended architecture’s linker exists and resolves within that root, and that package records and installed files are associated with the intended root. Don’t require identical absolute paths or host mutations. The discussion file itself recommends keeping linker-anchoring tests in staging or target roots and limiting live-host tests to safe cases. (discussion, lines 21–42)
