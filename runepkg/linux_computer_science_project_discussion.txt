At a Linux systems and ELF/dynamic-linker computer science level, the ELF specification and kernel execution model are identical across all three cases—every dynamically linked ELF executable carries a PT_INTERP program header pointing to its dynamic linker path (such as /lib64/ld-linux-x86-64.so.2 or /lib/ld-linux-aarch64.so.1), which the kernel (fs/binfmt_elf.c) loads before transferring control to _start.

However, whether the package manager should apply identical symlink/anchoring mutations across all three roots differs because the target namespace and mutation boundary differ:

1. Why the ELF & Symlink Mechanics Are Identical in Principle
PT_INTERP resolution: When the kernel execs a dynamically linked ELF binary, it reads PT_INTERP (for example, /lib64/ld-linux-x86-64.so.2 on x86_64 or /lib/ld-linux-aarch64.so.1 on aarch64) and maps that interpreter into the new process address space.

Symlink path semantics (POSIX readlink / namei): A symlink like /lib64/ld-linux-x86-64.so.2 -> ../usr/lib/x86_64-linux-gnu/ld-linux-x86-64.so.2 is resolved relative to the directory containing the symlink (<root>/lib64), staying inside <root> when accessed inside a chroot or prefix-aware staging root.

Staging/target roots (install_dir and --target=...): Because those roots are isolated trees rather than the active process/host namespace, materializing libc6 (Stage 0) and ensuring the ld-linux symlink points to a real target inside that tree makes the root self-contained and chroot- or qemu-ready.

2. Why Live Host / Should Not Run Identical Unconditional Linker/Runtime Mutation Logic
On a live Linux host (and especially a live WSL/Kali environment), ld-linux and libc.so.6 are already mapped into running processes and managed by the host's primary glibc / dpkg state:

Atomic replacement vs. symlink/file churn: Replacing or unlinking an active dynamic linker or libc.so.6 in place without atomic rename/version coordination—or overriding core runtime packages on /—can break dlopen / execve for processes that start mid-transaction or leave runepkg and dpkg out of sync.

Host package ownership: On live /, libc6 and ld-linux-x86-64.so.2 already belong to the host OS. Treating live / identically to an empty staging root by forcing/re-anchoring core runtime links by default risks clobbering host-managed links or version constraints.

3. How to Align the Mental Model Cleanly
Same resolution rule, different root policy: All three targets care about valid ld-linux symlink targets and libc6 (Stage 0) availability for their respective root, but live / should guard/shield core runtime mutations by default while alternate install roots and cross-target sysroots anchor ld-linux and Stage 0 automatically.

If you want deterministic verification on live / without risking breakage: Inspect /lib64/ld-linux-x86-64.so.2 (file and file -L) and runepkg vs. dpkg state first, and only test live-/ package installs on a non-critical leaf package without --force—or in a disposable container/distro copy.
