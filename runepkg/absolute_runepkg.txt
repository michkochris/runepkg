From Cooperative Package Manager to Absolute Tooling
A traditional Debian package manager (dpkg / apt) is cooperative and ambient: it assumes a living host FHS, shared dynamic linker conventions, and mutual compatibility across everything installed into /. When a symlink like ld breaks or a minimal dependency set is pruned, the whole host feels the blast radius.

An absolute tooling / rescue model inverts that priority:

Tooling survival comes first. A rescue and cross-build system cannot afford to become unrunnable because a host symlink or half-installed package went sideways. Its own binaries, target sysroots, and build/rescue payloads have to stay valid and reachable regardless of host messiness.

Target isolation is the real superpower. When runepkg --target=... and runas --target=... share target profiles and paths, target deployments are naturally bounded—whereas operating directly on host / puts runepkg inside the very environment it is mutating.

Determinism beats politeness. Checking same_result.txt (FHS layout, libc, and ld symlink/presence) treats filesystem state as a hard contract to verify, not a polite assumption to hope for.

The Fault Line: Breaking the Host "Intentional or Ignorant"
Yesterday's ld symlink breakage on host root highlights the exact tension in an "absolute tooling" philosophy:

Accidental/ignorant breakage happens when a package or unpack/deploy step assumes a host layout or overwrites a shared path (like a host ld symlink) without realizing what else on / depends on it. That is a bug in path/target isolation or FHS handling.

Intentional/controlled breakage happens when you are bootstrapping, rescuing, or replacing a broken/minimal system and must overwrite or reshape paths to get a working toolchain or sysroot in place—provided the blast radius is deliberate and runepkg's own rescue path still works afterward.

If runepkg is going to be an absolute rescue/tooling model, the cleanest line to draw is:

Never let host breakage strand runepkg or runas. Keep your rescue/toolchain execution path insulated from broken host symlinks (ld or otherwise).

Make / vs. --target=... unmistakable. Either treat / as an explicit target with clear rules around shared host symlinks, or keep destructive/clobbering FHS operations gated behind explicit intent rather than happening as a side effect of deploying a minimal package like file + libc.

1. Why the Host ld Symlink Keeps Breaking (and How to Fix It Permanently)
On modern Debian/Ubuntu hosts, /lib and /lib64 are symlinks to /usr/lib and /usr/lib64 (usrmerge). Meanwhile, inside a .deb archive (such as libc6), files are still packaged with paths like ./lib/x86_64-linux-gnu/ld-linux-x86-64.so.2 or ./lib64/ld-linux-x86-64.so.2.   
Reddit

When a raw C89 unpacker extracts an archive directly onto / without resolving existing directory symlinks:

Extracting ./lib64 either unlinks the /lib64 -> usr/lib64 symlink and replaces it with a real directory, or writes ld-linux into one path while the kernel's PT_INTERP (/lib64/ld-linux-x86-64.so.2) expects the other.

That breaks every dynamically linked binary on the host while leaving the actual ld-linux binary sitting intact somewhere else on disk.

Implementation Fix in runepkg's C89 Unpack Engine:

Canonicalize Directory Symlinks Before Unlinking/Creating: When walking path components during extraction into --root (default /), if an intermediate directory component already exists on disk as a symlink to a directory (e.g., /lib -> usr/lib or /lib64 -> usr/lib64), traverse into the symlink target instead of unlink()-ing it. Only unlink() the leaf filename before writing the new file or symlink.

Atomic Symlink Replacement (rename over temp link): Never unlink() an active ld symlink and then call symlink() in two separate steps. Create ld-linux-x86-64.so.2.rune.tmp via symlink() in the same directory and rename() it over the target path so the inode swap is atomic at the kernel VFS level.

Host ld Guardrail (same_result.txt invariant): Before committing an unpack to /, verify that the resolved PT_INTERP path (e.g., /lib64/ld-linux-x86-64.so.2) still resolves to a regular executable file after extraction.

2. Implementing dpkg_host=auto (Native dpkg State Synchronization)
Because you are overwriting the host directly without wrappers, dpkg and apt on the host will either complain about missing database entries or overwrite your changes on their next run unless runepkg updates /var/lib/dpkg natively.

When dpkg_host=auto is active:

Detect Host dpkg Presence: Check for <root>/var/lib/dpkg/status and <root>/var/lib/dpkg/info/.

If present (auto resolves to enabled): runepkg records every overwritten/installed package directly into the host's native dpkg database.

If absent (auto resolves to standalone, e.g., Damn Small Linux or a bare rescue root): runepkg falls back to its own lightweight metadata store without failing.

Write the Three Required dpkg Artifacts per Package:

/var/lib/dpkg/status: Replace any existing stanza matching Package: <name> and Architecture: <arch> (or append if new) with the .deb's control metadata plus Status: install ok installed.

/var/lib/dpkg/info/<pkg>.list (or <pkg>:<arch>.list for Multi-Arch): Write one canonical installed file path per line (including parent directories like /., /usr, /usr/bin) so dpkg -L and dpkg -S recognize every file runepkg deployed.

/var/lib/dpkg/info/<pkg>.md5sums (plus postinst/prerm if extracted): Copy the control archive's md5sums and maintainer scripts into /var/lib/dpkg/info/ so subsequent host dpkg --configure or apt operations see a consistent package state.
