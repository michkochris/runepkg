In the Debian package management system (dpkg/APT), Conflicts, Breaks, and Replaces are fields declared in a package's control file. They define relationships between packages, telling the system how to handle installations, upgrades, and file overwrites without causing system instability.Here is a breakdown of how each one works, their key differences, and when they are used.1. ConflictsThe Conflicts field is a hard barrier. It states that two packages absolutely cannot be unpacked or installed on the system at the same time.Behavior: If you try to install Package A, and it Conflicts with Package B (which is already installed), APT will refuse to install Package A unless Package B is completely removed first.Common Use Case: When two packages provide the exact same service or software, but in different variations. For example, mailx-bsd and mailx-heirloom cannot coexist because they are different implementations of the same tool.2. BreaksThe Breaks field is a softer, version-aware restriction introduced to replace Conflicts in many scenarios, especially during system upgrades. It states that installing Package A will break Package B unless Package B is also upgraded to a compatible version.Behavior: It prevents a specific version (or range of versions) of a package from being configured alongside another. Instead of forcing a flat-out removal, it signals to APT: "You can install me, but you must also upgrade or modify the broken package at the same time so they don't crash each other."Common Use Case: Used heavily during major software updates. If an upgraded shared library (Package A) changes its API, it will Break an older application (Package B) that relies on the old API. This forces APT to upgrade Package B simultaneously.3. ReplacesThe Replaces field allows a package to overwrite files that legally belong to another package, or to completely take over its spot. By default, dpkg will error out if Package A tries to install a file that Package B already placed on the disk. Replaces grants permission to do this.Behavior: On its own, it allows file overwriting. However, it is almost always paired with either Conflicts or Breaks.Common Use Case (with Breaks): When a software suite reorganizes its files. For example, if a file moves from package-common to package-core, package-core will declare it Replaces and Breaks the older version of package-common.Common Use Case (with Conflicts): When Package A is a complete functional replacement for Package B. Declaring both will remove Package B entirely and let Package A take over its files.Direct ComparisonFieldCan they be installed together?Primary PurposeWhat happens during installation?ConflictsNoPrevents two incompatible packages from existing at the same time.Forces the removal of the conflicting package.BreaksYes (if versions match)Prevents breaking an older version of another package during upgrades.Forces APT to update or manage the broken package to a safe version.ReplacesDependent on pairingAllows a package to safely overwrite files owned by another package.Overwrites specific files without throwing a packaging error.Practical Example: Splitting a PackageImagine a package named text-editor that contains both the core text editor and a bunch of plugins.
