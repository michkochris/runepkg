If you drop a static musl full extended runepkg binary onto a Debian/glibc system (like Damn Small Linux) and run runepkg sync, runepkg update, and runepkg -i file pulling in minimal pruned dependencies including libc and libgcc_s1, you do not get a clean, reliably working set of those tools on a broken root filesystem. Here is why that theory breaks down in practice:

Static musl runepkg survives, glibc-linked payloads do not: Because runepkg itself is statically linked against musl, runepkg won't fail to start due to missing shared libraries on a broken host. However, Debian .deb packages like file, libc6 (or libc), and libgcc-s1 are built against glibc (and often expect specific dynamic loader paths like /lib64/ld-linux-x86-64.so.2, symbol versions, or directory layouts). If the host's dynamic linker or core glibc paths get clobbered or pruned, those unpacked .deb binaries and libraries can fail to load or run even though they were extracted to disk.

Pruned dependencies and dpkg_host=auto can break the host before or during extraction: Installing minimal/pruned dependencies into / while also syncing dpkg state (dpkg_host=auto) can overwrite or remove files that existing host tools or the dynamic linker rely on. Once core shared libraries or /lib//lib64//usr/lib symlinks are altered or missing on /, existing host commands and newly unpacked glibc binaries can break immediately—leaving you with a working runepkg binary, but not guaranteed working file utilities or host libraries.

Database state vs. actual filesystem health: Recording file, libc, and libgcc_s1 in runepkg's binary tracking and updating dpkg state only proves those packages were registered/unpacked—it does not guarantee their runtime dependencies, dynamic loader links, or /etc//usr paths still work on a broken / root.
