The mystery of why runepkg upgrade leaves your host ld symlink healthy while runepkg -i file breaks it comes down to package scope, missing toolchain dependencies, and the aggressive healing logic in the Psychic Subsystem (runepkg_psychic_reconcile_ld_symlink).
Here is the exact breakdown of why this happens:
1. What runepkg -i file Installs vs. What It Misses
When you run runepkg -i file, runepkg resolves and installs file and its minimal runtime dependency chain (10 packages):
•
gcc-16-base, libgcc-s1, libc6, libc-gconv-modules-extra, libmagic-mgc, libmagic1t64, libbz2-1.0, liblzma5, zlib1g, file.
Notice what is not in that list: binutils (which provides the actual GNU linker binaries like x86_64-linux-gnu-ld.bfd).
2. The Trigger: runepkg_psychic_reconcile_ld_symlink()
At the end of any top-level runepkg -i installation  runepkg_install.c, runepkg invokes  runepkg_psychic_reconcile_ld_symlink() to ensure /usr/bin/ld isn't broken:
1.
It loops through linker candidates (x86_64-linux-gnu-ld.bfd, aarch64-linux-gnu-ld.bfd, ld.bfd, ld.gold).
2.
Because binutils was never installed during runepkg -i file, none of those candidate binaries exist on disk.
3.
Failing to find a valid candidate, the reconciler falls back to its default behavior: it unlinks /usr/bin/ld and forces a symlink to x86_64-linux-gnu-ld — which points to nowhere because binutils isn't there.
4.
Result: /usr/bin/ld becomes a dangling symlink, breaking the host's linker!
(Additionally, because bash wasn't part of those 10 packages, any script invoking #!/bin/bash like /usr/bin/ldd threw a bad interpreter error).
3. Why runepkg upgrade Succeeds
When you run runepkg upgrade, runepkg processes 398 full system packages, which explicitly includes binutils, binutils-x86-64-linux-gnu, bash, dash, and all core FHS packages:
•
When runepkg_psychic_reconcile_ld_symlink() runs after upgrading, x86_64-linux-gnu-ld.bfd actually exists on disk.
•
The reconciler successfully matches the candidate, links /usr/bin/ld to a valid target, and leaves your host linker fully operational.
How to Fix It (The "Absolute Tooling" Way)
If you want runepkg -i (or installing isolated packages like file) to never break host symlinks when toolchain packages are absent, you have two choices:
1.
Conditional Reconciliation Check: Update runepkg_psychic_reconcile_ld_symlink() in  runepkg_psychic.c so that if no linker candidate binary exists on disk, it refuses to touch or unlink /usr/bin/ld rather than falling back to a dangling symlink.
2.
Auto-Include Binutils for Dev Packages: Or, treat linker/toolchain reconciliations as conditional on binutils being present in the installed set.
