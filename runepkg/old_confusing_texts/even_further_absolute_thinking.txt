In Debian, libtool explicitly lists the file package as a runtime dependency (Depends: file) because libtool scripts invoke the file utility during compilation and linking to inspect what kind of file an input is (using magic numbers and file headers).   
File Extensions

Why libtool Needs file
Identifying build artifacts and libraries: During build, link, and install phases, libtool handles object files (.o, .lo), static archives (.a), shared libraries (.so), and libtool archive files (.la). Checking file types helps scripts distinguish real libraries/binaries from scripts, text files, or archives.   
File Extensions

Enforcing package integrity in dpkg: dpkg -r only removes a single package and checks whether other installed packages depend on it. Because libtool declares a hard dependency on file, dpkg stops the removal to prevent a broken dependency state.

What to Do Next
Check if you need libtool: libtool is a developer/build tool for building shared and static libraries (commonly alongside Autotools). If you are not compiling software from source, you probably do not need it.

Use apt instead of raw dpkg -r: Run apt-cache rdepends file to see everything on your system that depends on file. If you want to remove file and let Debian handle dependency resolution cleanly, use sudo apt remove file (which will also remove libtool if it depends on file).

Avoid --force-depends for normal use: Forcing removal with dpkg --force-depends -r file bypasses the check, but any subsequent libtool build that calls file can fail or behave unexpectedly.

how would maintainer scripts mess with my precious ld symlink?

Maintainer scripts (preinst, postinst, prerm, and postrm) run arbitrary shell or binary commands during package unpacking, configuration, removal, and purging. In a custom runepkg / runas workflow or pruned rootfs, they can touch an ld symlink in several concrete ways:

Ways Maintainer Scripts Affect ld Symlinks
Alternative registration and removal (update-alternatives): A postinst script for a linker or toolchain package may register or switch an ld alternative (--install / --set / --auto), while a prerm or postrm script may call --remove. If the target binary is missing in your pruned rootfs or sysroot, the resulting symlink dangles.

Direct symlink creation, replacement, or cleanup: Scripts sometimes create or update convenience symlinks (for example /usr/bin/ld or a triplet-prefixed link) on install (postinst) or remove symlinks on prerm/postrm using rm -f or ln -sf. If a script runs against the wrong root prefix or assumes a file exists that was pruned out, it can overwrite or delete your symlink.

Trigger activation and ldconfig hooks: postinst or dpkg triggers often invoke ldconfig or regenerate linker/alternative state. While ldconfig manages shared library soname links rather than /usr/bin/ld itself, failed or skipped hooks during partial/forced runs can leave symlink or cache state out of sync.

Host vs. target root leakage: If a maintainer script runs unchrooted or without proper root-prefix isolation during a cross-build or teardown test, commands in postinst/prerm/postrm can mutate host paths instead of your target rootfs or sysroot.

How to Inspect and Guard Against It
1
Extract and read maintainer scripts
1 min
Inspect the control archive of suspect .deb packages (such as binutils or split packages in target_deb/) before running them.
Check preinst, postinst, prerm, and postrm for ln, rm, update-alternatives, or hardcoded /usr/bin/ld paths.
Verification: You see every command in the scripts that creates, modifies, or removes ld or points to /usr/bin/ld.

2
Scope script execution to the target root
2 min
Run maintainer scripts inside the target root context (such as chroot with proper path/environment setup) rather than against the host / when testing rootfs teardown or arm64 sysroot builds.
Verification: Script actions affect only the target root path and leave the host's ld symlink untouched.

3
Verify ld before and after script hooks
2 min
Record the ld symlink target before and after running preinst/postinst or prerm/postrm.
Run ls -la and readlink -f on the ld path after each phase.
Verification: readlink -f resolves to an existing linker binary whenever a linker is expected in that layer, or the symlink is cleanly absent when pruned.
