0. HISTORICAL CONTEXT & WHY THIS IS A MAJOR CHALLENGE
--------------------------------------------------------------------------------
In the early Unix era (1970s–1980s, AT&T UNIX / Version 7 / BSD), systems were
built from small, composable command-line utilities (`ar`, `tar`, `mkdir`, `rm`,
`cp`, `ln`, `chmod`, `chown`, `touch`, `readlink`) connected by pipes, standard
I/O, and exit statuses—later consolidated in embedded Linux by tools like BusyBox
and later GNU coreutils.

Rebuilding 14 classic Unix utilities and archive/compression handlers inside a
single clean-room ISO C89 static rescue binary (`musl-gcc -static`) under GPLv3,
unifying symlinks and cross-target paths via `runepkg_psychic.c` and
`runepkg_antimatter.c`, and finishing the architecture with a separate `arch-utils`
repository is a major systems-engineering challenge for six concrete reasons:

1) Early-Unix Composability vs. Single-Binary Rescue Reliability:
   Early Unix relied on separate binaries and `PATH` lookup; rescue environments
   break when `PATH`, shared libraries, or core binaries are missing or damaged.
   Exposing these 14 capabilities as internal `runepkg` command-line options or
   applets while avoiding external `exec`/`PATH` shellouts requires strict
   separation between CLI argument/I/O dispatch and pure C89 core functions.

2) Strict C89 Standard Constraints Without Modern Shortcuts:
   ISO C89 forbids mixed declarations and code, `//` line comments in strict
   mode, variadic macros in older dialects, and many modern POSIX conveniences
   unless explicitly guarded. Implementing archive parsers, decompression streams,
   cryptographic/checksum routines (`MD5`, `SHA-256`), symlink reconciliation,
   and syscall wrappers in portable C89 demands disciplined memory management
   and zero undefined behavior.

3) Filesystem & Rescue Edge Cases (Symlinks, Permissions, Atomicity):
   Operations like `rm -rf`, `ln`, `cp`, `chmod`, `chown`, and `touch` operate
   directly on live or target filesystems. Symlink loops, traversal (`..`),
   broken loader links, partial writes, permission errors, and interrupted
   operations can corrupt a host or sysroot if rollback, bounds checks, and
   error handling are incomplete.

4) Archive & Compression Format Complexity:
   Handling `ar` archives, USTAR/GNU/PAX `tar` headers, and `gzip`/`xz`/`zstd`
   streams cleanly—while guarding against malformed headers, truncated streams,
   and decompression/extraction bombs—adds substantial parser and state-machine
   complexity.

5) Symlink & Cross-Target Profile Unification (`psychic` + `antimatter`):
   Keeping symlink/link reconciliation (`runepkg_psychic.c`) and cross-target
   profile/path unification (`runepkg_antimatter.c`) aligned with `runepkg`
   without letting target rules leak into low-level format parsers or symlink
   fixes create loops requires clean layered interfaces.

6) Clean-Room GPLv3 Provenance & Test Discipline:
   Maintaining strict GPLv3 clean-room provenance (keeping GPLv2 trees such as
   BusyBox out of the workspace and code) while verifying every utility with
   deterministic plain-text shell I/O checks (`runepkg_same_result?.txt`,
   `runepkg_same_test?.sh`) and `PATH=/nonexistent` tests requires ongoing
   audit discipline across `runepkg` and `arch-utils`.

3. DUAL-LAYER ZERO-DEPENDENCY STATIC RESCUE CORE + PSYCHIC/ANTIMATTER LAYERS
--------------------------------------------------------------------------------
Eliminate 100% of runtime external tool shellouts (/usr/bin/ar, tar, gzip, xz,
zstd, cp, rm, mkdir, ln, chmod, chown) from the low-level rescue core. Compile a
single, indestructible ~536 KB static ELF binary (`musl-gcc -static`) that operates
unconditionally even on a completely wiped host environment (`PATH=/nonexistent`).

Existing / Active Symlink & Target Unification Modules in runepkg:
- runepkg_psychic.c / .h
  - Symlink and link-reconciliation engine ("psychic" pre-flight and recovery):
    inspects symlink chains, repairs dangling/broken dynamic linker and path
    links, detects symlink loops, and sets links right before or during rescue
    and extraction operations.
- runepkg_antimatter.c / .h
  - Cross-target profile and path unification module (last in the series to
    arrive): unifies target architecture profiles, sysroot roots, and path
    rules across native, cross-target, and rescue contexts so path and target
    handling stays consistent across the codebase.

The 15 Clean-Room C89 Modules (runepkg_*matter):

[ Archive & Stream Layer ]
1. runepkg_truematter.c / .h
   - Magic-byte format detection (ar, tar, gz, xz, zst, ELF) & path traversal (..)
     security enforcement prior to archive extraction.

2. runepkg_darkmatter.c / .h
   - Clean-room C89 ar archive header parser. Replaces runtime calls to /usr/bin/ar,
     parsing debian-binary, control.tar*, and data.tar* entries directly from stream.

3. runepkg_exomatter.c / .h
   - High-level .deb container orchestrator. Validates control metadata, debian-binary
     versioning, and delegates member extraction to stream handlers.

4. runepkg_fluxmatter.c / .h
   - Unified decompression stream dispatcher bridging zlib (.gz), xz-embedded/liblzma
     (.xz), libzstd (.zst), and uncompressed raw streams to the tar parser.

5. runepkg_rawmatter.c / .h
   - Safe zero-shell chunked I/O stream engine with configurable memory buffers
     and POSIX rlimit boundary checks to prevent extraction bombs.

6. runepkg_submatter.c / .h
   - Clean-room C89 streaming USTAR tar parser. Extracts files, directories, and
     metadata in a single pass without temporary disk expansion.

7. runepkg_oddmatter.c / .h
   - Extended tar format handler managing GNU longnames, BSD archive variants, and
     PAX extended header attributes.

[ Filesystem & Metadata Layer ]
8. runepkg_neomatter.c / .h
   - Recursive directory creator (mkdir -p), file cloner, and atomic temporary file
     staging engine utilizing rename() for fail-safe transactional extraction.

9. runepkg_voidmatter.c / .h
   - Non-symlink-following safe recursive directory/file removal engine with rollback
     journaling to protect host system paths during package purge.

10. runepkg_mirrormatter.c / .h
    - Direct symlink (symlink()) and hardlink (link()) creation primitives with
      chroot/sysroot jail containment checks.

11. runepkg_spinmatter.c / .h
    - Metadata restoration engine restoring file permissions (chmod), ownership
      (lchown), and microsecond timestamps (utimensat) matching package specs.

[ Rescue & FFI Bridge Layer ]
12. runepkg_nullmatter.c / .h
    - Zero-external-binary rescue router directing package operations away from broken
      host binaries to internal clean-room primitives.

13. runepkg_redmatter.c / .h
    - Emergency host repair engine for diagnosing and fixing corrupted dpkg status
      stanzas, broken symlinks, and missing shared library anchors.

14. runepkg_protomatter.c / .h
    - Target rootfs / chroot / /mnt/runepkg bootstrapper for bare-metal sysroot
      creation and initramfs rescue image deployment.

15. runepkg_graymatter.c / .h
    - Static C89 <-> C++ ABI FFI bridge connecting the low-level rescue core with
      the C++ high-level network and resolver engine.


4. SEPARATE REPOSITORY FINISHER: `arch-utils` (GPLv3 CLEAN-ROOM C89 SUITE)
--------------------------------------------------------------------------------
To finish off the architecture cleanly without bloating runepkg's rescue core,
the 14 classic utilities are modeled as a separate companion repository named
`arch-utils` under GPLv3 in ISO C89 (`musl-gcc -static`).

`arch-utils` entails a clean-room ISO C89 utility suite—built with musl libc
and licensed under GPLv3—that gives developers, users, and sysadmins direct,
low-level control over archives, compression streams, filesystem trees,
symlinks/metadata, and integrity hashes without relying on external host binaries
or dynamic libraries.

The Four Functional Pillars of `arch-utils`:
1) Archive & Stream Unpacking (ar, tar, gzip, xz, zstd):
   - Inspecting and unpacking .deb containers (ar), tarballs (tar), and compressed
     streams without calling external host tools.
2) Directory, File, & Link Control (mkdir, rm, cp, ln, readlink):
   - Building target trees, copying payload files, creating hard/symbolic links,
     and resolving link chains or jail boundaries via runepkg_psychic awareness.
3) Permission, Ownership, & Timestamp Restoration (chmod, chown, touch):
   - Restoring exact POSIX modes, numeric UID/GID ownership, and microsecond
     timestamps on extracted or staged files.
4) Checksum & Integrity Verification (md5sum, sha256sum):
   - Calculating and checking file or payload digests (MD5, SHA-256, FNV-1a)
     before trusting or deploying archives.

What a User / Sysadmin Uses `arch-utils` For:
1) Broken or Minimal Rescue Shells:
   - Operating under `PATH=/nonexistent` or inside an initramfs / recovery chroot
     where `/bin/tar`, `/usr/bin/ar`, or `/bin/rm` is missing, damaged, or linked
     against broken shared libraries.
2) Cross-Target Staging & Rootfs Prep:
   - Assembling and inspecting root filesystems for alternate target architectures
     (arm64, riscv64, etc.) where setting modes, links, and timestamps cleanly
     matters more than full distro bloat.
3) Deterministic Scripting & Verification:
   - Running lightweight, predictable commands in shell scripts or plain-text
     I/O verification suites (`runepkg_same_test?.sh` / `runepkg_same_result?.txt`)
     with deterministic exit codes and zero runtime surprises.
4) Container, Embedded, & CLFS Build Environments:
   - Providing lightweight, self-contained utilities that operate without pulling in
     large userland packages, toolchain dependencies, or dynamic loader chains.

Why a Static Clean-Room Suite Matters:
When a Linux system is healthy, nobody thinks about tar, ar, ln, or chmod—until libc
or binutils breaks mid-upgrade, a dynamic linker symlink points into thin air, or you
are staring at a half-built rootfs with almost nothing working. Having a small,
static, clean-room C89 utility suite (`musl-gcc -static`) that works unconditionally
when the host environment is corrupted is the difference between a fast 5-minute
recovery and reinstalling from scratch.


5. EXPLICIT REPLACED UTILITIES MATRIX & SPECIFICATION
--------------------------------------------------------------------------------
To achieve absolute zero-dependency rescue capability on broken or bare-metal host
systems and finish the suite in `arch-utils`, runtime execution of 14 external
host utilities is eliminated and exposed as clean command-line options / built-in
applets or standalone/multi-call `arch-utils` tools:

1) Utility: `ar` (`/usr/bin/ar`)
   - Replaced Shell Command : `ar x <package.deb>` / `ar t <package.deb>`
   - Implementation Module  : `runepkg_darkmatter.c` / `runepkg_darkmatter.h` (and `arch-utils` ar applet)
   - Clean-Room C89 Function: Parses BSD/GNU/Debian 60-byte magic `ar` headers
     (`!<arch>\n`), extracting `debian-binary`, `control.tar.*`, and `data.tar.*`
     payload streams directly in memory without calling `/usr/bin/ar`.

2) Utility: `tar` (`/bin/tar`, `/usr/bin/tar`)
   - Replaced Shell Command : `tar -xf`, `tar -C`, `tar -cf`, `tar -ztf`
   - Implementation Modules : `runepkg_submatter.c` (USTAR) & `runepkg_oddmatter.c` (GNU/PAX) (and `arch-utils` tar applet)
   - Clean-Room C89 Function: Implements single-pass 512-byte header streaming parser
     supporting POSIX USTAR headers, GNU `L`/`K` long filename records, and PAX
     extended header attributes without intermediate disk extraction or `/bin/tar`.

3) Utility: `gzip` / `gunzip` (`/bin/gzip`, `/usr/bin/gzip`)
   - Replaced Shell Command : `gzip -d`, `gunzip -c`, `gzip -9`
   - Implementation Module  : `runepkg_fluxmatter.c` / `runepkg_fluxmatter.h` (and `arch-utils` gzip/gunzip applet)
   - Clean-Room C89 Function: Direct stream decompression of `.gz` and `.tar.gz`
     payloads via integrated `zlib` API, bypassing external `/bin/gzip` binaries.

4) Utility: `xz` / `unxz` (`/usr/bin/xz`)
   - Replaced Shell Command : `xz -d`, `unxz -c`, `xz -dc`
   - Implementation Module  : `runepkg_fluxmatter.c` / `runepkg_fluxmatter.h` (and `arch-utils` xz/unxz applet)
   - Clean-Room C89 Function: Direct stream decompression of LZMA2 `.tar.xz` archives
     using `xz-embedded` / `liblzma` API, eliminating external `/usr/bin/xz` binaries.

5) Utility: `zstd` / `unzstd` (`/usr/bin/zstd`)
   - Replaced Shell Command : `zstd -d`, `unzstd -c`, `zstd -dc`
   - Implementation Module  : `runepkg_fluxmatter.c` / `runepkg_fluxmatter.h` (and `arch-utils` zstd/unzstd applet)
   - Clean-Room C89 Function: Direct stream decompression of modern `.tar.zst` payloads
     using static `libzstd` C API, removing runtime `/usr/bin/zstd` dependencies.

6) Utility: `mkdir` (`/bin/mkdir`)
   - Replaced Shell Command : `mkdir -p <dir_path>`
   - Implementation Module  : `runepkg_neomatter.c` / `runepkg_neomatter.h` (and `arch-utils` mkdir applet)
   - Clean-Room C89 Function: Iterative recursive directory tree creation utilizing POSIX
     `mkdir()` with canonical path sanitization, replacing external `/bin/mkdir` spawns.

7) Utility: `rm` (`/bin/rm`)
   - Replaced Shell Command : `rm -rf <path>`, `rm -f <file>`
   - Implementation Module  : `runepkg_voidmatter.c` / `runepkg_voidmatter.h` (and `arch-utils` rm applet)
   - Clean-Room C89 Function: Non-symlink-following safe recursive directory and file
     purging using `unlink()`, `rmdir()`, and POSIX `opendir()`/`readdir()` with
     rollback safety journals to prevent accidental host path corruption.

8) Utility: `cp` (`/bin/cp`)
   - Replaced Shell Command : `cp -a`, `cp -f`
   - Implementation Module  : `runepkg_neomatter.c` / `runepkg_neomatter.h` (and `arch-utils` cp applet)
   - Clean-Room C89 Function: High-throughput chunked file copying and atomic temporary file
     staging using POSIX `read()`, `write()`, and atomic `rename()`.

9) Utility: `ln` (`/bin/ln`)
   - Replaced Shell Command : `ln -s <target> <link>`, `ln <target> <link>`
   - Implementation Module  : `runepkg_mirrormatter.c` / `runepkg_mirrormatter.h` + `runepkg_psychic.c` (and `arch-utils` ln applet)
   - Clean-Room C89 Function: Direct creation of symbolic links (`symlink()`) and hard
     links (`link()`) with chroot/sysroot boundary containment and symlink sanity checks.

10) Utility: `chmod` (`/bin/chmod`)
    - Replaced Shell Command : `chmod <mode> <path>`
    - Implementation Module  : `runepkg_spinmatter.c` / `runepkg_spinmatter.h` (and `arch-utils` chmod applet)
    - Clean-Room C89 Function: Direct POSIX `chmod()` mode bit restoration for files and
      directories matching `.deb` control metadata specs.

11) Utility: `chown` (`/bin/chown`)
    - Replaced Shell Command : `chown <uid>:<gid> <path>`
    - Implementation Module  : `runepkg_spinmatter.c` / `runepkg_spinmatter.h` (and `arch-utils` chown applet)
    - Clean-Room C89 Function: Direct POSIX `lchown()` ownership restoration for files,
      symlinks, and directories without resolving user/group names through host shellouts.

12) Utility: `touch` (`/usr/bin/touch`)
    - Replaced Shell Command : `touch -t`, `touch -r`
    - Implementation Module  : `runepkg_spinmatter.c` / `runepkg_spinmatter.h` (and `arch-utils` touch applet)
    - Clean-Room C89 Function: Microsecond access/modification timestamp restoration
      using POSIX `utimensat()` / `utimes()` directly on file descriptors.

13) Utility: `md5sum` / `sha256sum` (`/usr/bin/md5sum`, `/usr/bin/sha256sum`)
    - Replaced Shell Command : `md5sum -c <md5sums>`, `sha256sum <file>`
    - Implementation Modules : `runepkg_hash.c` & `runepkg_md5sums.c` (and `arch-utils` md5sum/sha256sum applets)
    - Clean-Room C89 Function: In-memory FNV-1a, MD5, and SHA-256 calculation and verification
      against `.deb` control `md5sums` records without external utility invocations.

14) Utility: `readlink` (`/bin/readlink`)
    - Replaced Shell Command : `readlink -f <path>`
    - Implementation Module  : `runepkg_truematter.c` / `runepkg_truematter.h` + `runepkg_psychic.c` (and `arch-utils` readlink applet)
    - Clean-Room C89 Function: Direct POSIX `readlink()` resolution, symlink chain/loop
      handling, and path canonicalization to enforce path traversal jail containment
      without external shell execution.

6. STRUCTURAL BOUNDARIES FOR DECOUPLING THE 14+ UTILITIES
--------------------------------------------------------------------------------
Because all 14 utilities live inside one static binary and share low-level C89
modules—and also map to the standalone `arch-utils` repo—coupling can easily
occur if CLI parsing, target profile logic, symlink fixes, stream state, and
syscalls leak across files. We enforce six strict structural boundaries:

1) Separate CLI / Applet Dispatch from Core Logic:
   - Rule: main() and option/applet parsing belong only in the CLI dispatch layer
     (runepkg_cli.c / runepkg_nullmatter.c, and arch-utils dispatch). Each utility
     entrypoint parses argc/argv into a plain C89 config struct and calls a pure
     library function.
   - Why: Neither tar nor rm nor chmod reads global CLI flags or writes formatted status
     messages directly if a higher-level orchestrator (runepkg_exomatter, runepkg_redmatter,
     runepkg_protomatter) or arch-utils calls the same underlying operation.

2) Route Streams Through Narrow Interfaces, Not Concrete Parsers:
   - Rule: Keep archive detection (runepkg_truematter), container parsing (runepkg_darkmatter,
     runepkg_submatter, runepkg_oddmatter), decompression (runepkg_fluxmatter), and chunked
     I/O (runepkg_rawmatter) decoupled via small read/write/seek stream structs and
     explicit error codes rather than direct cross-module calls or global state.
   - Why: gzip, xz, and zstd all feed decompressed bytes into tar or raw readers; isolating
     stream state per handle allows swapping compression backends without touching tar
     header logic or leaking static buffers across calls.

3) Isolate Symlink Fixes and Cross-Target Profile Unification:
   - Rule: Keep symlink/link reconciliation in `runepkg_psychic` and cross-target
     profile/path unification in `runepkg_antimatter` rather than scattering target
     path heuristics or link-fix logic across parsers and filesystem helpers.
   - Why: `runepkg_psychic` sets link state and symlink resolution right while
     `runepkg_antimatter` unifies target profiles and paths cleanly without
     mutating low-level parser state or global buffers.

4) Isolate Filesystem Mutations by Responsibility:
   - Rule: Keep distinct filesystem actions in dedicated modules instead of mixing them:
     - Path checks & canonicalization       : runepkg_truematter + runepkg_psychic
     - Directory creation, copy, atomic rename: runepkg_neomatter
     - Non-symlink removal & rollback journal: runepkg_voidmatter
     - Symlink/hardlink & jail checks       : runepkg_mirrormatter + runepkg_psychic
     - chmod, lchown, & microsecond timestamps: runepkg_spinmatter
     - Checksums (MD5 / SHA-256 / FNV-1a)   : runepkg_hash.c, runepkg_md5sums.c
   - Why: Archive extractors emit a normalized entry descriptor (path, type, mode, uid/gid,
     mtime, digest, stream) and hand it to the filesystem layer, so cp, ln, chmod, chown,
     touch, and rm remain reusable as standalone applets with identical safety rules.

5) Forbid Hidden Global State and Cross-Layer Back-Calls:
   - Rule: In strict C89, avoid mutable file-scope globals where reentrant per-operation
     context structs work. Enforce a strict unidirectional dependency hierarchy:
     - Top    : CLI & orchestration (runepkg_exomatter, runepkg_nullmatter, runepkg_redmatter, runepkg_protomatter, runepkg_antimatter)
     - Middle : Format/stream engines, symlink reconciliation (runepkg_psychic), & utility operations
     - Bottom : Syscall wrappers, bounds/path checks, and checksums
   - Why: Lower layers never call upward into orchestration or C++ (runepkg_graymatter),
     preventing circular dependencies and PATH=/nonexistent execution failures.

6) Lock Decoupling In with Per-Applet Contract Tests:
   - Rule: Test each of the 14 utilities both in isolation (unit/CLI checks with fixed
     inputs, temp dirs, and PATH=/nonexistent) and end-to-end inside .deb extraction
     (runepkg_same_test?.sh / runepkg_same_result?.txt), covering both runepkg and
     arch-utils.
   - Why: If changing runepkg_neomatter, runepkg_psychic, runepkg_antimatter, or
     runepkg_truematter breaks cp, ln, readlink, or mkdir, per-utility contract tests
     pinpoint the exact breach immediately.
