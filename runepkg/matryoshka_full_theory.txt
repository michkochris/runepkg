That Russian nesting-doll (matryoshka) analogy is spot-on: when you open a package like file, inside it is a dependency like libc6, and inside that are shared libraries, dynamic loaders, symlinks, and runtime hooks that everything else depends on.

The issue isn't just "installing file along with libc6 before an upgrade"—it's dependency ordering, live-root mutation order, and runtime coupling:

1. Why Order Matters Like Nesting Dolls
Inner layers must exist and remain coherent before outer layers rely on them:
If a new binary or library expects a newer symbol, path layout, or loader behavior from libc6, installing the dependent package before the underlying library/symlink setup is consistent—or swapping libc6 out from underneath running binaries—breaks the chain.

Notice in your previous log that libc6 was shielded, while gcc-16-base, libgcc-s1, libc-gconv-modules-extra, and file still ran in that transaction. A single broken symlink, overwritten library path, or missing interpreter target during extraction is enough for execve() to fail with ENOENT.

2. Why Live / Is Unforgiving for Core Runtime / Toolchain Packages
On a live system (/), dpkg and apt have decades of special-case ordering (Pre-Depends, unpack vs. configure phases, ldconfig triggers, protected essential packages, and staged replacement) specifically because replacing core runtime pieces (libc6, dynamic linker, libgcc-s1, coreutils/shell) in place can pull the rug out from under active processes.

If runepkg is installing directly to / without full dpkg pre-dependency/configure sequencing:

Topological / dependency order matters: Dependencies should be ordered so prerequisites are in place before dependents are configured—and core runtime packages (libc6, libc-bin, dynamic linker, etc.) should generally be blocked or explicitly gated on live / rather than auto-upgraded as a side effect of installing a small utility like file.

Test against a non-live sysroot/root first: Running runepkg -i against a staging/test sysroot directory (instead of live /) lets you verify dependency order, file placement, and symlinks with zero risk of bricking your WSL Kali shell.
